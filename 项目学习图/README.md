## 全项目一句话架构

```
Electron GUI / Textual TUI / CLI  ──TCP 127.0.0.1:7437 · NDJSON · JSON-RPC 2.0──▶  iwan-core daemon
                                                                                    ├─ SocketServer（每行一个 asyncio Task）
                                                                                    ├─ SessionManager（每会话一把锁 + 一个沙箱根）
                                                                                    ├─ AgentRunner（每 run 新建）→ 5 种执行引擎
                                                                                    ├─ ToolRegistry（64 内置工具 + MCP 工具）
                                                                                    ├─ PermissionManager / Sandbox / Trust / Shadow 回滚
                                                                                    └─ Scheduler / WorkflowEngine / BackgroundTaskRegistry
```

## 一图看懂：五个值得学的设计决策

1. **单连接并发 + 每会话串行**：`socket_server._read_loop` 对每行 `create_task`（`socket_server.py:365`），所以长跑的 `session.send_message` 不会堵住同连接的 `permission.respond`；并发上限由 `SessionManager` 的 per-session `asyncio.Lock` 控制（`session/manager.py:314-327`）。
2. **沙箱根存 ContextVar 而非全局变量**：会话 cwd 变了只改当前 Task 上下文（`sandbox.py:495-528`），两个会话的 `validate_path` 各自解析到自己的项目目录——有单测 `tests/unit/test_sandbox.py:888` 钉死。
3. **事件是唯一 UI 真相**：daemon 只广播事件（`EventBus` → `IpcEventBroadcaster`），客户端本地不推断状态；`run.started` 新带 `session_id` 就是为了让多 run 事件按权威锚点归属，而不是靠"goal 文本恰好等于用户原话"猜。
4. **工具调用有影子副本**：`shadow.prepare → invoke → commit`（`tools/invocation.py:322-362`），配合 `files.changes` / `files.restore` 实现文件级回滚。
5. **装配层注入而非互相 import**：`WorkflowEngine`/`Scheduler` 只接收回调，由 `CoreApp` 在 `app.py:2344-2402` 装配——这就是为什么这三个子系统能各自单测而不起 daemon。
6. **"发送在途"按会话记账，不是窗口级开关**：`sendingSids: Set<string>` + 每 run 一个流式槽位（`streams: Map<runId,…>`），所以同一窗口里两个工作区能各跑一条任务、各流各的字；GUI 还能一进程开多扇窗并排看两个工作区（详见 [17 号评估](17-质量评估-多工作区并行能力.md)）。
