# 12 状态图 · run / 工作流节点 / 后台子任务

**回答的问题**：除"会话"之外，系统里还有三层各自独立的状态机，它们的状态取值从哪来、终态怎么判定。

## 图 A：一次 run（ExecutionContext）

```mermaid
stateDiagram-v2
    direction LR
    [*] --> running : run_and_capture 开始
    running --> success : context.mark_success（模型不再要工具）
    running --> failed : mark_failed(max_steps)
    running --> failed : mark_failed(llm_error)
    running --> failed : mark_failed(cancelled)
    success --> [*]
    failed --> [*]

    note right of failed
        三种 reason 都在 RunFinishedEvent.reason 里

    end note
```

## 图 C：后台子 Agent（BackgroundTaskRegistry 的推断状态）

```mermaid
stateDiagram-v2
    direction LR
    [*] --> running_bg : register(task)
    running_bg --> success_bg : task done + ctx.status=success
    running_bg --> failed_bg : task done + 异常 或 ctx.status≠success
    running_bg --> cancelled_bg : registry.cancel / cancel_batch / shutdown
    success_bg --> pruned : prune(ttl=3600s)
    failed_bg --> pruned
    cancelled_bg --> pruned
    pruned --> [*]

    note right of pruned
        优先按 cancelled_at → finished_at → created_at 判定过期
        清理时顺带 rmtree(run_dir) 并收缩空批次
    end note
```

## 读图要点

1. **状态来自"谁写"，不是"谁猜"**：run 的终态由 `ExecutionContext.mark_*` 决定；工作流节点终态由 `WorkflowEngine` 在 `await_child` 返回后 `record_node`；子 Agent 状态由注册表**推断**（`task.cancelled() / exception / ctx.status`），不是单独字段维护——少一份真相就少一处不一致。
2. **fail-fast 是刻意的**：`WorkflowExecutor` 单节点异常即 `raise RuntimeError`（`executor.py:157`），同层其它节点会被取消；要"部分成功继续跑"得自己在外层拆工作流。
3. **取消有三种来源但只有一个终态**：用户 `workflow.cancel`、daemon 关停 `shutdown()`、节点超时——最终都落 `cancelled`，区别只在 `reason`。
4. **`interrupted` 是"上一个进程死了"的墓志铭**：`mark_orphans_interrupted()` 在 `server.start()` **之前**执行（`app.py:2389-2392`），保证客户端第一眼看到的不是永远转圈的 `running`。
